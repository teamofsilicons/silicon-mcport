# Architecture

MCPort has a central Rust gateway, a public Rust client package, a stateful CLI with an outbound host daemon, and a configuration website (a Next.js server that keeps each sign-in and calls the gateway with bearer tokens).

## Identity and permissions

Identity is Silicon Accounts. Every request carries a Silicon Accounts access token issued to the `mcport` app; the gateway verifies it locally against the cached Accounts JWKS (EdDSA, audience, issuer, expiry) and refuses tokens issued before the account signed out, rotated its key or removed MCPort's access. Execution, provider-account changes, sharing, deletion and host creation also introspect the token with Silicon Accounts (answers reused for 30 seconds). The gateway issues no sessions or cookies.

Records key accounts by their permanent uuid and display their current `c:`/`si:` id. A plaintext `accounts` table caches each account's kind, id, profile, custodian and revocation time, filled from tokens, lookups (cached, within Accounts' rate limit) and the signed Accounts webhook, which is deduplicated by event id and applies only changes newer than what it already holds. Custodian data that grants someone access is re-checked with Accounts when older than ten minutes.

Everything belongs to an account: a connection belongs to its creator. Its managers are the owner and, for a Silicon owner, the Silicon's custodian; managers change configuration, share, delete and set tool policies, and never act as the Silicon. Visibility is `invited` (the owner and the accounts it added; owner-only with no grants) or `circle` (also the owner's circle: a Carbon and the Silicons it looks after). Grants name accounts by uuid. Sharing with a Silicon outside the sharer's circle requires the Silicon or its custodian to have allowed the sharer first. Global and per-account denies are checked at dispatch. Every discovered tool starts enabled unless a persisted deny applies. When an owner removes MCPort's access its connections are frozen for others; when it is deleted they are deleted.

The directory combines an attributed, bundled community snapshot, readable by everyone signed in, with personal templates visible to their creator, the creator's custodian and accounts they are shared with. Selection copies public configuration into a new connection, whose permissions and credentials are independent. Template edits never change configured connections. Catalog command suggestions are not execution authority: local registration and absolute executable approval still apply.

Provider credentials have their own lifecycle. Shared mode selects the owner's grant; personal mode selects the caller's grant. A custodian may inspect and disconnect, but not create, its Silicon's personal grants. OAuth uses protected-resource discovery, issuer binding, PKCE S256 and an exact callback. Refresh has no automatic retry after an uncertain response. Disconnect/reconnect fences pending OAuth attempts with an account epoch. Discovery supports protected-resource path/root fallback, RFC 8414 and ordered OIDC metadata, and the scopes from the provider’s Bearer challenge. Registration prefers an explicit public client ID, then advertised Client ID Metadata Documents when the gateway has a configured public HTTPS URL, then dynamic client registration. Metadata and callbacks come from configured URLs, never request headers. Only public PKCE clients are supported; confidential clients and automatic runtime scope upgrades are not implemented. Discovery falls back only on 404/410, never after unsafe or malformed metadata, and uses the first advertised authorization server.

## Execution

Cloud HTTP calls execute centrally through bounded MCP transports. Public destinations require HTTPS, DNS validation and pinned public addresses. Redirects and environment proxies are disabled. Operators may explicitly allow exact private origins for controlled environments; clients cannot override this policy.

Local HTTP and stdio execute through a registered host. The daemon connects outward, authenticating with a host-specific token. Jobs carry connection IDs, methods, arguments and verified actor context; they never carry arbitrary endpoints, commands or provider credentials. The local registry is authoritative. Per-user process/transport sessions are isolated, bounded and invalidated when credentials or configuration change. The daemon separately checks registered MCP availability with bounded protocol handshakes (at most four concurrently), using each account’s own configuration and no tool/resource calls. Existing stdio sessions are reused for liveness to avoid a competing process. Status starts as checking, becomes ready/offline after a check, and returns to checking when evidence is stale. Host and protocol health are separate; a health snapshot never prevents an authorized call from trying its normal timeout. Health is normally refreshed within 50 seconds, with longer checking states on very large registries.

Before dispatch the gateway revalidates the caller's account state (not signed out since the call was accepted), its access to the connection, the connection revision, the provider account and tool policy. Local leases are durable and not re-leased. The daemon journals acceptance before execution and retries result delivery, not execution. Modern and legacy MCP negotiation are supported. Schemas are discovered in the executing account/session and validate inputs and structured outputs.

Calls record the caller, selected provider account, method, timestamps, progress and outcome. Results are encrypted and belong to the caller; the caller's custodian may read them, connection owners may not. Download indices select bytes already in a result, with current access and original tool-policy checks. Local asset materialization only fetches literally returned URLs at the configured HTTP endpoint's exact origin under `/assets/`, with strict path, byte, count and time limits. It never reads arbitrary files or follows redirects.

## Persistence and lifecycle

This version runs one gateway process over SQLite WAL with full synchronous durability. AES-256-GCM encrypts record bodies using record- and owner-bound authenticated data. The data directory is mode 0700 and key/database files are mode 0600 on Unix. Back up both the encrypted database and its protected master key. Do not deploy multiple independent gateway writers: family and dispatch coordination currently use in-process locks.

The access upgrade atomically converts stored `private` connections to `invited` and removes their dormant invitations, preserving owner-only use. Legacy clients may still send `private`: creation becomes invited with no grants, and an owner-only reset clears invitations in the same transaction as the update. Provider credentials, connection IDs and tool policies stay intact.

Schema steps are numbered with `PRAGMA user_version` and only add tables and columns. Records written before Silicon Accounts keep their fields verbatim (typed reads preserve unknown fields) and stay unreachable until the operator re-keys them with `mcport-server link-identities`, which rewrites identity fields, derived record ids, owner columns and the authenticated data in one transaction, keeps the original identity in `legacy_*` columns and each value's `legacy` record, converts connections that earlier releases made visible to everyone around their owner into `circle` connections, with explicit grants for accounts outside the circle that used them, and can be re-run with another mapping before cutover.

Public resource creation allocates a compact ID in the same SQLite `IMMEDIATE` transaction as the encrypted record. A persisted arbitrary-width base62 cursor traverses each complete width through a seeded affine bijection; it does not truncate random identifiers, retry random collisions, or grow early. Three-character IDs provide 62³ = 238,328 values, followed by four, five, and further widths. A global allocation ledger survives resource deletion and environment cleanup. Failed transactions roll back both allocation and creation. These public locators are not security credentials. Telemetry uses a separate deterministic UUID namespace for compact invocation IDs and retains legacy UUID correlations.

The additive migration leaves legacy records and references unchanged and reserves existing public IDs. New idempotent calls have compact public IDs plus a private, tenant-scoped replay index committed with the call. Existing hash-keyed calls remain replayable without dispatching again. Environment cleanup removes those replay mappings with their call records but preserves the allocation cursor and ledger. Backups must include the whole database; do not reset the allocator or restore its tables independently of records. Rolling back to an older binary after compact keyed calls have been created would bypass the new replay index and can repeat upstream actions, so use a coordinated database/application backup rollback rather than a binary-only downgrade.

Silicon Accounts webhooks are verified over the exact body bytes (HMAC-SHA256, five-minute tolerance) before parsing. They can only narrow authority (revocations, removed access, deletion) or refresh displayed and custodian data; they never grant access by themselves.

## Client boundary

`mcport-core` contains wire types. `mcport-api` implements stateless HTTP operations; every request carries an explicit Silicon Accounts access token for the `mcport` app. `mcport-client` is the public facade and re-exports that API. Its `accounts` feature (default) signs in as MCPort's public client at Silicon Accounts (device flow for Carbons, short-lived token exchange for Silicons, refresh and revoke with `client_id` alone; no secret ships in a client). Its `session` feature keeps one sign-in in one owner-only file and refreshes it single-flight under a file lock, because a used refresh token ends the whole sign-in. Its `local` feature exposes registry mapping, account selection, configuration, runtime status/start/stop, the version 1 to 2 registry migration and an embeddable host connector. Local helpers accept the signed-in account's uuid, paths and executables explicitly. They do not discover a home or sign-in; in-memory configuration is saved only when the caller requests it.

The CLI depends only on `mcport-client` for MCPort functionality. Its adapters own command parsing, prompts, output and protected home storage: one sign-in per home and backend, and host registries per backend and host. Refresh is serialized across processes. The discovery commands (`accounts --json`, signed-out `login status --json`, `--help`) need no runtime, network or home. `mcport-daemon` depends on `mcport-api`, avoiding a facade/runtime cycle; it keys local provider accounts by the uuid each job carries (registry version 2) and still runs registries written before 0.3.0, for which the service sends their old keys, until `mcport host migrate` rewrites them. Neither transport nor facade performs implicit sign-in, refresh or mutation retries. Host-internal job endpoints remain distinct from ordinary user commands.

Unsupported interactive capabilities are explicit failures, not implied success. Proofs issued to other apps (Silicon Accounts User verification) are not accepted yet; `mcport.connections.read` and `mcport.tools.call` are reserved scopes. A separate MCPort API-key contract requires an explicit authority design.
